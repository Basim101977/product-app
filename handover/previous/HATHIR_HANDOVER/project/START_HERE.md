# ابدأ من هنا — حاضر على النوتبوك

هذه حزمة تطوير مشروع قائم، وليست برنامجًا جديدًا ولا نسخة من حسابات المستخدمين. لا تنشئ مشروع Firebase بديلًا ولا تنشر تلقائيًا.

نسختا HTML الحالية والتاريخية داخل الحزمة منقّحتان بموافقة المالك لإزالة بيانات ثابتة قديمة فقط. الأصل والمنشور لم يتغيرا. اقرأ بيان التنقيح ونتيجة الاختبارات قبل أي استخدام كنقطة انطلاق؛ الحزمة ليست نسخة استرجاع حرفية للواجهة المنشورة.

## ١. اقرأ وافحص الحزمة

افتح هذا المجلد في كودكس على النوتبوك. اطلب منه: «اقرأ AGENTS.md وHANDOVER.md ووثائق docs، ثم تحقق محليًا من الحزمة دون تعديل المشروع أو الاتصال ببيانات المستخدمين».

تأكد من وجود `PACKAGE-VERIFICATION.md` و`FILE-MANIFEST.json` و`source` و`support`. بعد تثبيت Node.js شغّل من جذر الحزمة:

```powershell
node support/verify-package.cjs
```

يجب ألا يظهر أي ملف مفقود أو متغيّر. هذا الفحص للنسخة كما استلمتها؛ ثبّت بيان الحزمة الأصلي كمرجع ولا تُحدّثه لإخفاء اختلاف غير مفهوم.

## ٢. اقرأ معلومات التطوير

اقرأ `HANDOVER.md` ثم `docs/ARCHITECTURE.md` و`docs/DATA-AND-SERVICES.md` و`docs/KNOWN-ISSUES.md`. اقرأ كذلك `docs/SECURITY-AND-ACCESS.md` قبل تسجيل الدخول إلى Google.

المصدر المعتمد داخل:

```text
source/work/hathir-production-upgrade-20260922/app
```

النسخة الموجودة تحت `hathir-mobile-actions-20260919` مرجع اختباري قديم، ولا تُنشر.

## ٣. ثبّت المتطلبات ثم اختبر محليًا

اتبع الأوامر الدقيقة في `docs/SETUP-AND-TESTS.md`. تحتاج Node.js 22 وJava 21 ومكتبات الخادم وأدوات الاختبار المثبتة بملفات القفل. تنزيلها يحتاج إنترنت، لكن الاختبارات نفسها اصطناعية ومحلية، ولا تحتاج كلمة مرور Firebase.

باختصار، من جذر الحزمة بعد تثبيت Node وJava:

```powershell
npm.cmd ci --prefix support --ignore-scripts --no-audit --no-fund
npm.cmd ci --prefix source/work/hathir-production-upgrade-20260922/app/functions --ignore-scripts --no-audit --no-fund
# راجع وثيقة الإعداد لضبط JAVA_HOME أو PERSONAL_TEST_JAVA.
Set-Location support
npx.cmd --no-install playwright install chromium
npm.cmd run install:emulator
npm.cmd run check
npm.cmd test
```

لا تتجاوز اختبارًا فاشلًا. احتفظ بالمخرجات، وابدأ بتحديد هل السبب نقص اعتماديات أم تغييرًا في المصدر. راجع عدد الاختبارات الذي أثبته فحص النقل في `PACKAGE-VERIFICATION.md` بدل افتراض أن نجاحًا قديمًا يثبت جهازك الجديد.

## ٤. شاهد معاينة آمنة

من `support` شغّل:

```powershell
npm.cmd run preview
```

هذا الأمر ينتج معاينة اصطناعية باستخدام بيانات اختبار ويمنع الشبكة الخارجية. لا يفتح حسابًا حقيقيًا. راجع وثيقة الإعداد لمكان مخرجات المعاينة. لا تستخدم خادم ملفات عاديًا لواجهة الإنتاج باعتبارها بيئة اختبار؛ إعدادات Firebase المرفقة تخص الموقع الحقيقي.

## ٥. أعد صلاحية الوصول عند الحاجة فقط

الحسابات والطلبة والمحاضرات تبقى محفوظة في Firebase. استخدم حساب Google المخوّل وسجّل الدخول بنفسك إلى CLI. لا ترسل كلمة المرور إلى كودكس ولا تنقل ملف الجلسة من الكمبيوتر القديم:

```powershell
# من جذر الحزمة، عند الحاجة لمراجعة المشاريع المتاحة، لا للنشر:
node support/node_modules/firebase-tools/lib/bin/firebase.js login
node support/node_modules/firebase-tools/lib/bin/firebase.js projects:list
```

تأكد أن المشروع الصحيح `alqar-student-attendance-2026`، وأن موقعه `hathir`. إن لم يظهر، فالمشكلة في حساب Google أو صلاحياته وليست في كود التطبيق. لا تعالجها بإنشاء حساب خدمة بمفتاح قابل للتنزيل أو بمنح صلاحيات عامة بلا موافقة.

## ٦. قبل أول تعديل أو نشر

أكّد فهمك للصلاحيات الشخصية، وحساب الغياب الأسبوعي، ومصادر القوائم القديمة وطابور المزامنة. جهّز خطة تغيير صغيرة واختبارًا لها.

النشر مقفول عمدًا إلى أن تتوفر نسخة احتياطية معتمدة وأدلة الإصدار. النسخ الخاصة ومفاتيحها غير مرفقة. هذا ليس عطلًا يجب حذفه من الكود. لا تستخدم `--force` أو ملفات إثبات وهمية.

لا تمسح بيانات الموقع على هاتف الأستاذ، ولا تطلب إعادة إنشاء الحساب، ولا تعدّل السجلات الحقيقية من أجل تجربة أولية. اختبار الهاتف والكاميرا والصوت والمزامنة الفعلية يحتاج خطة اختبار منفصلة مصرحًا بها.
